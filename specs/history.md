## 🆔 20250907-01

**Дата:** 2025-09-07  
**Статус:** ✅ Реализовано  
**Модуль:** infra  
**Заголовок:** Инициализация проекта на основе TMA Next.js шаблона  
**Ссылка:** [initial-commit-hash](https://github.com/username/tutor-manager/commit/initial)

### 📖 Контекст
Необходимо начать с готовой, совместимой с Telegram Mini App основы, чтобы не тратить время на настройку SDK, тем, роутинга.

### ✅ Решение
Использован шаблон https://github.com/Telegram-Mini-Apps/nextjs-template.git — он предоставляет:
- Готовую интеграцию с `@tma.js/sdk`
- Поддержку `initData`, `themeParams`
- Примеры компонентов под Telegram UI
- Настроенный Next.js App Router

### ↔️ Альтернативы
- Создать проект с нуля → отклонено, слишком много рутины.
- Использовать другой шаблон → отклонено, этот официально поддерживается сообществом TMA.

### ⚠️ Последствия
- Все последующие компоненты должны использовать `useInitData`, `useThemeParams` из `@tma.js/sdk`.
- Стили должны соответствовать `tailwind.config.js` шаблона.
- Нельзя использовать SSR — только CSR.

## 🆔 20250908-01

**Дата:** 2025-09-08  
**Статус:** ✅ Реализовано  
**Модуль:** auth, onboarding, infra  
**Заголовок:** Интеграция Supabase, онбординг и проверка пользователя при входе  
**Ссылка:** [commit:20250908-01](https://github.com/username/tutor-manager/commit/20250908-01)

### 📖 Контекст
Нужно обеспечить авторизацию через Telegram, регистрацию пользователя в Supabase, хранение профиля в таблице `public.teachers` с RLS, а также показывать онбординг только новым пользователям. Оптимизировать проверку существования и улучшить UX запуска приложения.

### ✅ Решение
Добавлены API-роуты:
- `app/api/auth/telegram/route.ts` — прокси к Edge Function для валидации initData и выдачи сессии.
- `app/api/check-teacher/route.ts` — проверка наличия пользователя по `telegram_id` (service_role, HEAD+count).
- `app/api/register-teacher/route.ts` — создание `auth.users` (admin), upsert профиля в `public.teachers`, откат при ошибке, возврат реальной сессии через `signInWithPassword`.

Страницы:
- `app/onboarding/page.tsx` — онбординг с TMA initData, кнопками (shadcn/ui), Zustand для загрузки.
- `app/login/page.tsx` — отправка initData и установка сессии Supabase.
- `app/page.tsx` — проверка пользователя при входе и редирект (React Query).
- `app/terms/page.tsx`, `app/privacy/page.tsx` — заглушки для документов.

Инфраструктура:
- Клиенты Supabase: браузерный (`getSupabase`) и серверный (`getSupabaseAdmin/getSupabaseAnon`).
- Включён React Query провайдер (`QueryProvider`).
- Кастомная кнопка на базе shadcn/ui (`components/ui/button.tsx`).

База данных (подготовлено к применению):
- Таблица `public.teachers` (`id uuid PK → auth.users`, `first_name`, `username`, `photo_url`, `created_at`).
- Индекс по `id`.
- RLS политики: select/update/insert только для `id = auth.uid()`.

### ↔️ Альтернативы
- Проверять существование через клиентский anon-клиент и RLS → отклонено, может давать ложные отрицания.
- Хранить `telegram_id` как bigint → отклонено, риск потери точности в JS. Выбран текст.

### ⚠️ Последствия
- В окружении должны быть заданы: `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY` (только на сервере), `SUPABASE_AUTH_TELEGRAM_URL` (+ опционально `SUPABASE_AUTH_TELEGRAM_SECRET`).
- Email/Password провайдер в Supabase должен быть включён.
- Онбординг показывается только новым пользователям; существующие попадают сразу в `/app`.

Нужно завершить серверную часть авторизации через Telegram Mini App на Supabase Edge, а также улучшить UX старта: не создавать сессию для новых пользователей до подтверждения (кнопка «Начать»), и корректно маршрутизировать существующих пользователей сразу в приложение.

### ↔️ Альтернативы

- Требуются корректно заданные секреты в функции и `.env.local`.

## 🆔 20250917-01

**Дата:** 2025-09-17  
**Статус:** ✅ Реализовано  
**Модуль:** pricing, architecture, students  
**Заголовок:** Перенос цены за занятие из учеников в расписание — динамическое ценообразование  
**Ссылка:** [commit:20250917-01](https://github.com/username/tutor-manager/commit/20250917-01)

### 📖 Контекст
Хранение цены за занятие в таблице `students` ограничивало гибкость: невозможно менять цену для одного занятия, давать скидки, отслеживать историю. Требовалась модель, где цена привязана к конкретному событию, а не к пользователю.

### ✅ Решение
- **Удалено поле `price_per_lesson` из таблицы `students`.**
- Добавлены новые таблицы:
  - `lesson_templates` — шаблоны повторяющихся занятий (день недели, время, цена)
  - `lessons` — реальные занятия с фиксированной ценой на момент проведения
- Цена теперь хранится в `lessons.price` — точная, неизменяемая после создания.
- Цель: возможность задавать разные цены за одно и то же занятие у одного ученика (например, базовый тариф vs интенсив vs скидка).

### ↔️ Альтернативы
- Хранить цену в `students` и наследовать её → отклонено, потеря гибкости.
- Хранить историю цен в отдельной таблице → отложено до v2.

### ⚠️ Последствия
- Все новые занятия должны создаваться с явным указанием цены.
- Отчётность по доходам теперь работает корректно.
- Поддержка скидок, индивидуальных тарифов — теперь возможна.
- Модуль “Ученики” больше не содержит финансовую информацию — чёткое разделение ответственности.

## 🆔 20250117-01

**Дата:** 2025-01-17  
**Статус:** ✅ Реализовано  
**Модуль:** api, students, security, ui  
**Заголовок:** Полный CRUD API для учеников с контактами и родственниками  
**Ссылка:** [commit:25a1a0d](https://github.com/username/tutor-manager/commit/25a1a0d)

### 📖 Контекст
Требовалось создать полноценный REST API для управления учениками, их контактами и родственниками с соблюдением безопасности, типизации и валидации. Также необходимо было исправить проблему дублирования регистрации пользователей и улучшить UI с использованием shadcn/ui Drawer.

### ✅ Решение
**API Endpoints:**
- `/api/students` — GET (список), POST (создание с контактами и родственниками)
- `/api/students/[id]` — GET, PATCH, DELETE для конкретного ученика
- `/api/students/[id]/contacts` — GET, POST для контактов ученика
- `/api/students/[id]/contacts/[contactId]` — PATCH, DELETE для конкретного контакта
- `/api/students/[id]/relations` — GET, POST для родственников ученика
- `/api/students/[id]/relations/[relationId]` — PATCH, DELETE для конкретного родственника

**Безопасность:**
- JWT аутентификация через `Authorization: Bearer <token>`
- RLS (Row Level Security) — все запросы фильтруются по `teacher_id = auth.uid()`
- Валидация входных данных через Zod схемы
- Проверка владения данными на каждом уровне

**Типизация:**
- Обновлены схемы для поддержки `ContactType` enum из Supabase
- `RelationSchema` теперь включает `contact_type` с валидацией
- Полная типизация всех API ответов и запросов

**Инфраструктура:**
- Добавлен `getSupabaseForRequest()` для серверной аутентификации
- Обновлены хуки `useCreateStudent` и `useStudents` для использования API
- Добавлены comprehensive тесты для API

**UI улучшения:**
- Заменено модальное окно на shadcn/ui Drawer компонент
- Улучшен UX добавления контактов и родственников
- Добавлена валидация в реальном времени

**Исправления:**
- Устранена проблема дублирования регистрации пользователей
- Унифицирован процесс создания пользователей через Edge Function

### ↔️ Альтернативы
- Использовать GraphQL вместо REST → отклонено, REST проще для мобильных приложений
- Хранить контакты в JSON поле → отклонено, нужна индексация и валидация
- Создавать отдельные API для каждого типа контакта → отклонено, избыточная сложность

### ⚠️ Последствия
- Все операции с учениками теперь проходят через API с полной валидацией
- Безопасность обеспечивается на уровне базы данных через RLS
- Форма создания ученика теперь работает с реальным API
- Поддержка множественных контактов и родственников без ограничений
- UI стал более современным и соответствует Telegram дизайн-системе

Поле "Заметка" (note) было определено в Zod схеме и отображалось в UI форме, но не сохранялось в базе данных при создании или редактировании учеников. Требовалось добавить обработку этого поля в API маршруты.

### ✅ Решение
**API исправления:**
- В `app/api/students/route.ts` (POST) добавлено `note: values.note || null` в объект `studentData`
- В `app/api/students/[id]/route.ts` (PATCH) добавлена условная обработка: `if (values.note !== undefined) { (studentUpdateData as any).note = values.note || null; }`

**Проверка инфраструктуры:**
- Подтверждено наличие поля `note` в Supabase типах как `string | null`
- Подтверждено наличие поля в Zod схеме как `z.string().optional()`
- Подтверждена работа UI компонента `Textarea` для ввода заметок

### ↔️ Альтернативы
- Добавить поле в схему базы данных → отклонено, поле уже существует
- Изменить тип поля в схеме → отклонено, текущий тип корректен

### ⚠️ Последствия
- Заметки теперь корректно сохраняются при создании новых учеников
- Заметки корректно обновляются при редактировании существующих учеников
- Поле заметки работает идентично другим полям формы (имя, фамилия, адрес и т.д.)
- Данные заметок сохраняются между сессиями и доступны для просмотра
